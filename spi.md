# Part 1 — Foundations

## 1.1 — Why does SPI even exist?

Imagine your MCU (Microcontroller Unit — a tiny computer chip) needs to talk to a temperature sensor. In the old days, engineers used **parallel communication** — sending 8 bits at once meant using 8 separate wires.

```text
Parallel:  D0 D1 D2 D3 D4 D5 D6 D7   →  8 wires just for 8 bits
```

**What was wrong with that?**

- Too many pins needed — MCUs only have a limited number of pins
- More wires on the PCB (circuit board) = more space, more cost
- Signal integrity (how clean the signal stays) gets worse as wire count grows
- All 8 wires must arrive "in sync" — if even one is a tiny bit late, the whole byte reads wrong
- Longer distances mean more noise pickup on parallel wires

So engineers thought: **let's use fewer wires and send bits one after another (serially) instead.**

```text
Parallel communication
        ↓
Serial communication        (bits go one at a time on a single wire)
        ↓
Synchronous serial          (send a clock along with the data)
        ↓
SPI
```

### Why SPI and not UART or I²C?

- **UART** — the receiver doesn't *know* exactly when the next bit is coming. It just guesses based on a pre-agreed speed (baud rate). If both sides aren't set to the exact same speed, data gets corrupted.
- **SPI** — the controller sends its own clock signal along with the data. The receiver is told explicitly: "read *now*." No guessing needed — which is why SPI can run much faster than UART.
- **I²C** — uses only 2 wires, but adds addressing, ACK/NACK, and arbitration logic. That makes it flexible but a bit slower and more complex.

**SPI's trade-off:** use more wires, but keep the actual transfer mechanism as simple and fast as possible.

## 1.2 — A Simple Real-Life Analogy

Picture a classroom:

```text
Teacher                =  Controller (Master) — controls everything
Students                =  Peripherals (Slaves)
Bell's steady rhythm    =  Clock — tells everyone exactly when to speak
What's actually said    =  Data (MOSI/MISO)
Pointing at one student =  Chip Select — "you answer now, everyone else stay quiet"
```

> **Remember — this is only an analogy to build intuition. Now let's see what actually happens on the wires.**

## 1.3 — What SPI Actually Is

**SPI = Serial Peripheral Interface**

- **Serial** → bits travel one after another on a single wire
- **Peripheral** → any device outside the MCU (sensor, flash memory, display)
- **Interface** → the rules/method for connecting them

SPI is a **synchronous serial communication protocol** — both sides share the same clock signal, so exactly when to read a bit is never ambiguous.

Modern datasheets say **Controller/Peripheral** instead of the older **Master/Slave** — same meaning: one device runs the whole conversation, the others respond.

# Part 2 — The SPI Wires

```text
                 SPI CONTROLLER (MCU)
              ┌─────────────────┐
        SCLK ─┤                 ├──── Peripheral 1
        MOSI ─┤                 ├──── Peripheral 1
        MISO ─┤                 ├──── Peripheral 1
        CS1  ─┤                 ├──── Peripheral 1
        CS2  ─┤                 ├──── Peripheral 2
              └─────────────────┘
```

## 2.1 — SCLK / SCK (Serial Clock)

Generated by the controller — a steady, repeating digital signal. On every clock edge (a transition), one bit gets shifted or sampled.

## 2.2 — MOSI (Master Out, Slave In)

Data direction: Controller → Peripheral. (Newer naming: SDO on the controller side, sometimes called COPI.)

## 2.3 — MISO (Master In, Slave Out)

Data direction: Peripheral → Controller. Any peripheral that is *not* currently selected puts its MISO output into **tri-state** (high-impedance — it goes silent and doesn't push any voltage onto the wire). This is exactly what lets multiple peripherals share one MISO wire without conflict.

## 2.4 — CS / SS (Chip Select) — the most confusing part for beginners

Common intuition: HIGH = "on", LOW = "off". But CS works **backwards**:

```text
CS = HIGH  →  Peripheral is "asleep" — not listening (deselected)
CS = LOW   →  Peripheral is "awake" — actively listening (selected)
```

This is called **active-low**. **Why design it this way?** Because when nothing is happening (idle state), it's easy and safe to keep every CS line pulled HIGH by default (just a pull-up resistor) — and that means nothing gets accidentally selected.

```text
MCU:  CS_A = HIGH, CS_B = LOW, CS_C = HIGH
                     ↑
          Only Sensor B is active right now — everyone else is silent
```

# Part 3 — How a Single Bit Actually Moves

Say the controller wants to send the byte `10110010`.

The controller has a **TX shift register** — the byte sits there first. The peripheral has an **RX shift register** on its side.

On every clock edge:
1. The topmost (MSB — Most Significant Bit) bit in the TX register goes out on MOSI
2. At the exact same moment, whatever bit is on MISO shifts into the controller's RX register
3. The register shifts over by one position

```text
Before clock:  [1][0][1][1][0][0][1][0]
After 1 shift: [0][1][1][0][0][1][0][X]   ← one bit left, one new bit came in
```

| Clock Edge | MOSI (out) | TX Register (remaining) |
|---|---|---|
| 1 | 1 | 0110010_ |
| 2 | 0 | 110010__ |
| ... | ... | ... |
| 8 | 0 | empty — new byte ready |

**One clock pulse = one bit transferred (in BOTH directions at once!)**

> **The single most important insight about SPI:** it is inherently **full-duplex** — sending and receiving happen simultaneously. That's why, even when you only want to *read* data, the controller still has to push something (a **dummy byte**, usually `0x00` or `0xFF`) onto MOSI — because the clock only exists while data is being sent.

### Why is a shift register even needed?

Inside the MCU, data always exists as a whole **parallel** byte (all 8 bits at once). But the wire can only carry bits **serially** (one at a time):

```text
Parallel (byte)  ⇄  Shift Register  ⇄  Serial (one bit at a time on the wire)
```

- **Parallel-to-serial** (sending) — the byte loads into the register first, then one bit exits per clock
- **Serial-to-parallel** (receiving) — bits arrive one at a time on MISO, pile up in the register, and eventually form a complete byte

MSB-first (sending the most significant bit first) is the most common convention in SPI — though some devices use LSB-first, so always check the datasheet.

# Part 4 — CPOL and CPHA (the most confusing topic — fully explained)

## 4.1 — CPOL (Clock Polarity) — Where does the clock sit when idle?

```text
CPOL = 0  →  Clock idles (rests) LOW
CPOL = 1  →  Clock idles (rests) HIGH
```

## 4.2 — One Clock Pulse Has Two Edges — understand this first

```text
     ┌───────┐
_____│       │_____
     ↑       ↑
  1st edge  2nd edge
```

One pulse = going up (1st edge) + coming back down (2nd edge).

**Why does it need two separate edges at all?** If data *changes* and gets *read* at the exact same instant, that instant is electrically unstable — the receiver could catch a half-changed signal. So the rule is: **change the data on one edge, and read it on the other edge, once it's had time to settle.**

## 4.3 — CPHA Just Decides Which Edge Does What

```text
CPHA = 0  →  1st edge → sample (read) | 2nd edge → change
CPHA = 1  →  1st edge → change        | 2nd edge → sample (read)
```

A special consequence of CPHA=0: **the very first bit must already be ready before the clock even starts** (right when CS goes LOW), because the first edge is immediately used for sampling.

### How change/sample alternate across two pulses (CPHA=0 example):

```text
SCLK:  edge1(rise) edge2(fall) edge3(rise) edge4(fall)
        sample      change      sample      change
```

So across 2 pulses = 4 edges, **2 edges are for sampling and 2 are for changing** — alternating. No edge is "wasted" — each one just has a different job.

## 4.4 — All Four Modes

| Mode | CPOL | CPHA | Idle Clock | Sample Where |
|---|---|---|---|---|
| 0 | 0 | 0 | LOW | 1st edge (rising) |
| 1 | 0 | 1 | LOW | 2nd edge (falling) |
| 2 | 1 | 0 | HIGH | 1st edge (falling) |
| 3 | 1 | 1 | HIGH | 2nd edge (rising) |

**Key point:** CPHA always decides *which numbered edge* (1st or 2nd) does the sampling. Whether that edge is rising or falling depends only on CPOL.

### Mode 0 timing (the most common one):

```text
SCLK:  __/‾\__/‾\__/‾\__/‾\__
          ↑    ↑    ↑    ↑
        sample sample sample sample  (every rising edge)
MOSI:  ==D7==D6==D5==D4==D3==...
```

### Mode 2 timing (idle HIGH):

```text
SCLK:  ‾‾\__/‾‾\__/‾‾\__/‾‾\__
          ↑    ↑    ↑    ↑
        sample (every falling edge — because here the 1st edge is falling)
```

## 4.5 — Why does this actually matter?

If you pick the wrong mode (say the peripheral needs Mode 0 but you configured Mode 1), the controller ends up **sampling on the wrong edge**. Results:

- Sometimes the data looks completely random
- Sometimes it looks like the bits are shifted by one position (because you caught an old or half-changed bit, not full noise)

## 4.6 — How to Figure Out the Mode from a Datasheet

A datasheet will usually say something like:

> *"Clock idles low. Data is captured on the rising edge."*

- **Idles low** → CPOL = 0
- **Captured on rising edge, and from idle-low the very first transition is rising** → CPHA = 0
- So → **Mode 0**

## 4.7 — Where CPOL/CPHA Actually Get "Used" (Firmware Level)

Before starting a transfer, in firmware you set this **once**, in the MCU's SPI_CTRL register:

```cpp
SPI_CTRL |= (CPOL_0 | CPHA_0);   // Selected Mode 0
SPI_CTRL |= SPI_ENABLE;
```

Once set, you don't have to do anything manually per bit — the SPI hardware automatically applies the correct idle level and sampling edge for every single bit, forever, until you change the mode.

```text
In firmware  →  set once, before the transfer starts
In hardware  →  applied automatically for every byte/bit
```

# Part 5 — A Complete Worked Example: Sending 'A'

Say you want to send the character `'A'` using SPI Mode 0.

## Step 1 — What is 'A' in binary?

```text
'A' (character) → ASCII value 65 → hex 0x41 → binary 01000001
```

## Step 2 — Set CPOL/CPHA

```cpp
SPI_CTRL |= (CPOL_0 | CPHA_0);   // Mode 0
```

This choice comes from the datasheet of whatever sensor/device you're talking to — if this doesn't match, everything downstream will be wrong.

## Step 3 — Byte Loads into the TX Register

```cpp
SPI_DATA = 0x41;   // 01000001 loaded into the shift register
```

## Step 4 — CS Goes LOW

The peripheral "wakes up."

## Step 5 — Clock Starts, Bits Go Out One by One (full waveform):

```text
CS     ‾‾\_____________________________/‾‾
SCLK   ___/‾\_/‾\_/‾\_/‾\_/‾\_/‾\_/‾\_/‾\___
MOSI      0   1   0   0   0   0   0   1
          └───────── 0x41 = 01000001 ─────┘
                    (MSB first)
```

**This is where CPOL/CPHA are actually doing their job:**
- Clock idles LOW (CPOL=0) — so every pulse goes low→high→low
- On the first (rising) edge of every pulse, the peripheral samples that bit (CPHA=0) — after 8 rising edges, the peripheral has the complete byte

## Step 6 — CS Goes Back HIGH

Transaction complete.

## Step 7 — Status Check (in firmware)

```cpp
while (!(SPI_STATUS & TX_DONE)) { }   // or use interrupts/DMA instead
```

**Note:** during those same 8 clocks, the peripheral is *also* sending something back on MISO (full-duplex) — even if you don't need it, that data still lands in the controller's RX register.

# Part 6 — Timing (Setup/Hold — Electrical Level)

```text
        setup time    hold time
             ↓            ↓
MOSI  ───────████████████████───────
                    ↑
              sampling edge (SCLK)
```

- **Setup time** — how long *before* the sampling edge the data must already be stable
- **Hold time** — how long *after* the sampling edge the data must stay stable
- **Propagation delay** — the time a signal takes to physically travel from one point to another

**What happens if the clock runs too fast?** This isn't a software bug — it's an **electrical** problem. Voltage takes a small but nonzero amount of time to move from one level to another (rise/fall time). If the sampling edge arrives before the data has fully settled, the receiver catches the wrong (stale or mid-transition) bit — this is called a **setup/hold violation**.

# Part 7 — Connecting Multiple Sensors to One MCU

Say you want to connect 3 sensors to a single MCU.

```text
                 SPI CONTROLLER (MCU)
              ┌─────────────────┐
        SCLK ─┼───┬─────┬───────┼──── Sensor A
        MOSI ─┼───┼─────┼───┬───┼──── Sensor B
        MISO ─┼───┼─────┼───┼───┼──── Sensor C
        CS_A ─┼───┘     │   │
        CS_B ─┼──────────┘   │
        CS_C ─┼───────────────┘
              └─────────────────┘
```

## How many wires does this actually need?

**Common wrong guess:** each sensor needs its own 4 wires → 3 × 4 = 12 wires.

**Actual answer:** no.

```text
Shared (same for everyone)     → SCLK, MOSI, MISO  = 3 wires
Separate (one per sensor)      → CS                 = 3 wires
                                                       ─────────
                                                 Total = 6 wires
```

**Why does this work?** Because only one sensor "speaks" at a time (whichever one has CS LOW). The others keep their MISO outputs tri-stated (silent), so three sensors can share one MISO wire without ever colliding.

**Rule:** only one CS should ever be active at a time. If two peripherals try to drive MISO simultaneously, that's **bus contention** — electrically they fight each other, producing an invalid voltage level, and in the worst case even damaging hardware from excess current.

## Daisy-Chain SPI (an alternative approach)

When CS pins are scarce, devices can be chained one after another:

```text
Controller → Device A → Device B → Device C → (loops back to Controller)
```

All the devices together form one giant shift register. Advantage: fewer CS lines needed. Disadvantage: data for the last device in the chain takes more clock cycles to arrive, and if one device fails, the whole chain breaks.

# Part 8 — SPI vs UART vs I²C

| Aspect | UART | SPI | I²C |
|---|---|---|---|
| Clock | None (asynchronous) | Shared clock | Shared clock |
| Wires | 2 (TX/RX) | ≥4 | 2 (SDA/SCL) |
| Full duplex | Yes | Yes (natively) | No |
| Addressing | None | None (uses CS) | Yes (address byte) |
| Multi-device | Hard | Easy (extra CS) | Easy (same 2 wires) |
| Speed | Medium | Fastest | Low-medium |
| Error detection | Parity bit possible | Nothing built-in | ACK/NACK |

**Key distinction:** UART is a **byte stream** — no packet boundary, no address, no checksum (the application has to define all of that itself). SPI is closer to a **clocked bit-transfer mechanism** — it also has no packet format, address field, CRC, retry, or ACK built in. **All of that is defined by each peripheral's own protocol.**

# Part 9 — SPI Is Not a Complete Protocol!

This is **critically important** to understand:

```text
SPI                  →  Just the transport mechanism (electrical signaling + clocking + shifting + CS)
Peripheral protocol  →  What the bytes actually MEAN (commands, addresses, CRC, etc.)
```

An SPI flash memory transaction might look like: `Opcode → 24-bit Address → Dummy cycles → Data`
A sensor's transaction might look like: `Register Address → Dummy Byte → Response`

**SPI only tells you how to move bits — what those bits mean is entirely up to each peripheral.**

### Example: Reading Register 0x20

```text
CS ↓
MOSI:  [READ CMD] [ADDR 0x20] [DUMMY]
MISO:  [ ---xx--] [  ---xx--] [REGISTER DATA]
CS ↑
```

**Why is a dummy byte needed?** Because the sensor needs a little time (measured in clock cycles) to internally fetch the register value and load it into its own shift register. There's no separate "wait" signal in SPI — so the controller just keeps the clock running by sending dummy bits while the sensor gets ready.

# Part 10 — Register-Level SPI (Firmware Side)

Typical conceptual registers inside an SPI peripheral:

```text
SPI_CTRL    → enable, controller-mode, CPOL, CPHA, bit-order bits
SPI_BAUD    → clock divider (sets the speed)
SPI_DATA    → TX/RX data register
SPI_STATUS  → TX empty, RX full, busy, overrun/underrun flags
```

## Polling
```cpp
while (!(SPI_STATUS & TX_READY)) { }   // CPU just waits here — simple but inefficient
SPI_DATA = byte;
```

## Interrupt
When the SPI event happens, hardware fires an **interrupt** → an ISR (Interrupt Service Routine) runs → it reads/writes the data. Benefit: the CPU is free to do other work in the meantime.

## DMA (Direct Memory Access)
```text
Memory  ↕  DMA  ↕  SPI
```
The DMA controller moves data between memory and SPI without CPU involvement. Most efficient for large transfers — the CPU just kicks it off and gets a completion interrupt at the end.

## FIFO (First In First Out buffer)
With TX/RX FIFOs, the CPU doesn't have to wait for every single byte — several bytes can be queued ahead of time. Two classic failure modes: **overrun** (RX FIFO fills up and new data is lost) and **underrun** (TX FIFO runs empty but the clock keeps going, sending garbage).

# Part 11 — Performance (Clock Speed ≠ Throughput)

```text
SPI clock = 10 MHz  →  10 million bits/sec (theoretical)
8-bit transfer       →  10 MHz / 8 = 1.25 MB/s (theoretical max)
```

Actual throughput is always lower, because of: command/address/dummy byte overhead, gaps between CS transactions, software/driver overhead, DMA setup time, and the peripheral's own internal processing time.

**Clock speed ≠ application throughput** — this is an important engineering lesson.

---

# Part 12 — Electrical Layer and Signal Integrity

SPI can be logically correct and still **fail physically**:

- Long wires or breadboard connections increase capacitance and slow the signal down
- At high frequencies you can get **ringing, overshoot, undershoot, and reflections** (from impedance mismatches on the trace)
- **Ground bounce** and **crosstalk** (interference from a neighboring wire) both get worse at high speed

This is why: *"SPI works fine at 1 MHz but fails at 20 MHz"* is usually **not** a software bug — it's an **electrical/signal-integrity** problem.

# Part 13 — Debugging with a Logic Analyzer

Expected waveform:
```text
CS    ‾‾‾‾‾\__________________/‾‾‾‾‾
SCLK  ______/‾\_/‾\_/‾\_/‾\_________
MOSI  ======1===0===1===1===0======
MISO  ======0===1===0===0===1======
```

**Debugging checklist:**
1. Is CS toggling? No → software/config problem
2. Is SCLK visible? No → SPI controller configuration is wrong
3. Is the MOSI data correct? No → command/config is wrong
4. Is MISO responding? No → peripheral/wiring/power problem
5. Is the returned data wrong? → check mode/timing/command

# Part 14 — How to Read a Datasheet

Always look for: SPI timing diagrams, SCLK/SDI/SDO/CS pin names, CPOL/CPHA (or "SPI mode"), maximum clock frequency, setup/hold times, command format, register map, dummy cycles.

**Names vary across datasheets:**
```text
MOSI = SDI = DIN
MISO = SDO = DOUT
SCLK = SCK = CLK
CS   = NSS = SS = CE
```
Never assume direction just from a pin's name — always confirm against the datasheet.

# Part 15 — 3-Wire, Dual, Quad, Octal SPI

- **3-wire SPI** — MOSI and MISO share a single bidirectional line; controller and peripheral take turns driving it (with a turnaround delay) to save a pin.
- **Dual/Quad/Octal SPI** — instead of 1 bit per clock cycle, 2/4/8 bits move at once (using extra data lines) — mainly used in **SPI NOR Flash** to boost speed. These involve distinct command, address, dummy-cycle, and data phases.

# Part 16 — SPI Flash Memory Example

```text
MCU → SPI Flash
```
Common commands: read JEDEC ID, READ, WRITE ENABLE, PAGE PROGRAM, SECTOR ERASE. A **busy bit** in the status register tells you whether the flash is currently erasing/writing — you must poll this before sending the next command.

# Part 17 — C++ Driver Architecture

```text
Application
     ↓
Device Driver (e.g. TemperatureSensor)
     ↓
SPI Bus Driver (SpiBus)
     ↓
MCU HAL / Registers
     ↓
Hardware
```

```cpp
class SpiBus {
public:
    bool initialize();
    bool transfer(uint8_t tx, uint8_t& rx);   // send one byte, receive one byte
    bool write(const uint8_t* data, size_t size);
    bool read(uint8_t* data, size_t size);
};

class TemperatureSensor {
private:
    SpiBus& spi;   // dependency injection — sensor driver never touches MCU registers directly
public:
    explicit TemperatureSensor(SpiBus& bus) : spi(bus) {}
    uint8_t readRegister(uint8_t address);
};
```

**Concurrency:** if one SPI controller is shared across multiple threads/devices (Sensor, Flash, Display), two transactions must never overlap — use `std::mutex` or a transaction-level lock. **The entire command sequence (CS assert → command → data → CS deassert) must be atomic**, not just a single byte — otherwise another thread could interleave and corrupt the bus.

# Part 19 — Common Mistakes

1. Swapping MOSI/MISO
2. Wrong CS pin
3. Wrong SPI mode (CPOL/CPHA)
4. Wrong bit order (MSB/LSB)
5. Clock frequency set too high
6. Forgetting to connect ground
7. Voltage level mismatch (3.3V vs 5V)
8. CS timing errors (toggled too early/late)
9. Not sending dummy bytes when reading
10. Sending a new command while the peripheral is still busy
11. Multiple devices driving MISO at the same time
12. DMA buffer lifetime bugs (buffer reused before transfer finishes)
13. No timeout — driver hangs forever

```cpp
// Wrong — never times out
while (!spi_ready) { }

// Correct — always have a timeout
while (!spi_ready) {
    if (timeout_expired) return ERROR;
}
```

# Part 21 — Unique / Lesser-Known Insights

- SPI has no inherent packet boundary — **CS itself is the transaction boundary**
- Even a pure "read" requires the controller to generate a clock (by sending dummy bytes)
- SPI has no universal maximum clock speed — it depends on the controller, peripheral, PCB, and voltage
- A wrong CPHA doesn't produce pure random noise — it produces subtly wrong data
- A peripheral can be logically correct but electrically "unreachable" (due to bad wiring)
- In Quad SPI, the classic "one clock = one bit" idea breaks — one clock moves 4 bits at once

---

# Part 22 — Engineer's Final Checklist

- **Electrical correctness** — correct voltage levels, ground connected
- **Timing correctness** — correct CPOL/CPHA, clock frequency within datasheet limits
- **Protocol correctness** — command/address/dummy bytes sent correctly
- **Driver architecture** — clean separation of layers (application/device/bus/HAL)
- **Concurrency** — locking done at the transaction level, not per-byte
- **Error handling & timeout** — errors return properly instead of hanging forever
- **Performance** — polling/interrupt/DMA used appropriately for the situation
- **Debuggability** — clean enough design to trace easily on a logic analyzer
